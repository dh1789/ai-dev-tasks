# PRD: JWT 기반 사용자 인증 시스템

**문서 버전**: 1.0
**생성일**: 2026-03-13
**작성자**: AI Planning Agent
**프로젝트 타입**: Node.js/TypeScript (자동 감지)

---

## 1. 개요 및 목표

### 1.1 배경
사용자 인증은 웹 애플리케이션의 핵심 보안 기능이다. JWT(JSON Web Token) 기반 인증 시스템은 무상태(stateless) 아키텍처를 지원하면서도, Redis 블랙리스트를 통해 토큰 무효화 기능을 제공하여 보안성과 확장성을 동시에 확보한다.

### 1.2 목표
- JWT 토큰 생성/검증/리프레시를 포함한 완전한 인증 파이프라인 구현
- Redis 기반 토큰 블랙리스트로 즉시 토큰 무효화 지원
- 보안 모범 사례 준수 (OWASP 인증 가이드라인)
- 프로덕션 레벨의 에러 핸들링 및 로깅

### 1.3 범위
- **포함**: 토큰 생성, 토큰 검증, 토큰 리프레시, 토큰 블랙리스트(Redis), 인증 미들웨어
- **제외**: 사용자 등록/로그인 UI, OAuth2/소셜 로그인, 역할 기반 접근 제어(RBAC), 2FA

## 2. 기능 요구사항

### 2.1 토큰 생성 (Token Generation)
- **FR-001**: Access Token 생성 (짧은 만료 시간: 15분)
- **FR-002**: Refresh Token 생성 (긴 만료 시간: 7일)
- **FR-003**: 토큰 페이로드에 사용자 ID, 이메일, 역할 포함
- **FR-004**: RS256 또는 HS256 알고리즘 지원 (설정 가능)
- **FR-005**: 토큰 쌍(access + refresh) 동시 발급

### 2.2 토큰 검증 (Token Verification)
- **FR-006**: Access Token 서명 검증
- **FR-007**: 토큰 만료 시간 검증
- **FR-008**: 블랙리스트 확인 (Redis)
- **FR-009**: 잘못된 토큰에 대한 구체적 에러 메시지 반환
- **FR-010**: Express 미들웨어로 요청 파이프라인에 통합

### 2.3 토큰 리프레시 (Token Refresh)
- **FR-011**: 유효한 Refresh Token으로 새 Access Token 발급
- **FR-012**: Refresh Token 회전(Rotation) - 리프레시 시 새 Refresh Token도 발급
- **FR-013**: 이전 Refresh Token 자동 무효화
- **FR-014**: Refresh Token 재사용 감지 및 전체 토큰 무효화 (보안)

### 2.4 토큰 블랙리스트 (Token Blacklist - Redis)
- **FR-015**: 로그아웃 시 Access Token 블랙리스트 등록
- **FR-016**: 토큰 만료 시간에 맞춘 Redis TTL 자동 설정
- **FR-017**: 블랙리스트 조회 (토큰 검증 시 자동 확인)
- **FR-018**: Redis 연결 실패 시 페일세이프(fail-safe) 동작

## 3. 비기능 요구사항

### 3.1 성능
- **NFR-001**: 토큰 검증 응답 시간 < 50ms (Redis 조회 포함)
- **NFR-002**: 토큰 생성 응답 시간 < 100ms
- **NFR-003**: Redis 블랙리스트 조회 < 5ms (캐시 히트 시)

### 3.2 보안
- **NFR-004**: 비밀 키는 환경 변수로만 관리 (코드에 하드코딩 금지)
- **NFR-005**: 토큰 페이로드에 민감 정보(비밀번호 등) 포함 금지
- **NFR-006**: timing-safe 비교 사용 (타이밍 공격 방어)
- **NFR-007**: 모든 토큰 관련 실패를 보안 감사 로그에 기록
- **NFR-008**: HTTPS 전용 전송 (설정 가이드 제공)
- **NFR-009**: Refresh Token 재사용 감지 시 해당 사용자의 모든 토큰 무효화

### 3.3 안정성
- **NFR-010**: Redis 연결 실패 시에도 서비스 지속 (graceful degradation)
- **NFR-011**: 가용성 목표 99.9%
- **NFR-012**: 구조화된 에러 응답 (일관된 에러 코드 체계)

### 3.4 유지보수성
- **NFR-013**: 테스트 커버리지 90% 이상
- **NFR-014**: TypeScript strict 모드 적용
- **NFR-015**: 보안 감사 로깅 (인증 성공/실패, 토큰 블랙리스트 등록 등)
- **NFR-016**: JSDoc 또는 TSDoc으로 공개 API 문서화

## 4. 사용자 시나리오

### 시나리오 1: 정상 로그인 및 API 접근
1. 사용자가 이메일/비밀번호로 로그인 요청
2. 서버가 자격증명을 검증하고 Access Token + Refresh Token 발급
3. 클라이언트가 Access Token을 Authorization 헤더에 포함하여 API 호출
4. 인증 미들웨어가 토큰을 검증하고 요청을 허용
5. **기대 결과**: 200 OK 응답과 요청 데이터 반환

### 시나리오 2: 토큰 만료 후 리프레시
1. Access Token이 만료된 상태에서 API 호출
2. 서버가 401 Unauthorized 응답
3. 클라이언트가 Refresh Token으로 토큰 리프레시 요청
4. 서버가 새 Access Token + 새 Refresh Token 발급
5. 클라이언트가 새 Access Token으로 재요청
6. **기대 결과**: 새 토큰 쌍 발급 및 API 정상 접근

### 시나리오 3: 로그아웃 및 토큰 무효화
1. 사용자가 로그아웃 요청
2. 서버가 현재 Access Token을 Redis 블랙리스트에 등록
3. 동일 Access Token으로 API 호출 시도
4. **기대 결과**: 401 Unauthorized (블랙리스트된 토큰)

### 시나리오 4: Refresh Token 재사용 공격 감지
1. 공격자가 탈취한 이전 Refresh Token으로 리프레시 시도
2. 서버가 재사용 감지 (이미 회전된 토큰)
3. 해당 사용자의 모든 Refresh Token 무효화
4. **기대 결과**: 403 Forbidden + 사용자에게 재로그인 요구 + 보안 경고 로깅

## 8. 제약사항 및 가정

### 제약사항
- Redis 서버가 별도로 운영되어야 함
- HTTPS 환경에서만 프로덕션 배포 가능
- 토큰 비밀 키는 최소 256비트 강도 필요

### 가정
- Express 기반 HTTP 서버가 이미 구축되어 있음
- Redis 서버가 접근 가능한 상태
- 사용자 모델/데이터베이스가 별도로 존재 (이 기능 범위 외)
- 클라이언트는 Authorization: Bearer 헤더를 사용하여 토큰 전송
