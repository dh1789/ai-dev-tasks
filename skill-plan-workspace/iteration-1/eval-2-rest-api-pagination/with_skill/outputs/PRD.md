# PRD: REST API 커서 기반 페이지네이션

**문서 상태**: 승인 완료
**생성일**: 2026-03-13
**프로젝트 타입**: Node.js/TypeScript (Express)

---

## 1. 개요 및 목표

### 배경
기존 REST API는 offset 기반 페이지네이션을 사용하고 있으며, 대량 데이터(수백만 건) 처리 시 성능 저하가 발생한다. offset이 커질수록 DB가 앞선 모든 행을 스캔해야 하므로 응답 시간이 선형적으로 증가한다.

### 목표
- offset 방식을 대체할 커서(cursor) 기반 페이지네이션 시스템 구축
- 대량 데이터에서도 일관된 응답 속도 보장
- 기존 API와의 하위 호환성 유지
- 데이터 삽입/삭제 시에도 안정적인 페이지 탐색

### 핵심 가치
- **성능 일관성**: 페이지 위치와 무관하게 일정한 응답 시간
- **데이터 안정성**: 페이징 중 데이터 변경에도 누락/중복 없음
- **개발자 경험**: 직관적인 API 인터페이스

## 2. 기능 요구사항

### FR-1: 커서 인코딩/디코딩
- 커서는 Base64 인코딩된 JSON 객체로, 정렬 기준 필드 값을 포함
- 위변조 방지를 위한 서명(HMAC) 검증
- 복합 커서 지원 (예: `createdAt` + `id`)

### FR-2: 페이지네이션 쿼리 빌더
- Prisma ORM과 통합되어 커서 조건을 WHERE 절로 변환
- `first` (앞으로 N개) 및 `last` (뒤로 N개) 방향 지원
- 정렬 방향(ASC/DESC) 자동 처리

### FR-3: 페이지네이션 미들웨어
- Express 미들웨어로 요청 파라미터 파싱 및 검증
- 쿼리 파라미터: `cursor`, `limit`, `direction`
- 기본값: `limit=20`, `direction=forward`
- 최대 limit 제한 (기본: 100)

### FR-4: 표준 응답 포맷
- Relay 스타일 커넥션 응답 구조 채택
```json
{
  "data": [...],
  "pageInfo": {
    "hasNextPage": true,
    "hasPreviousPage": false,
    "startCursor": "eyJpZCI6...",
    "endCursor": "eyJpZCI6...",
    "totalCount": 1500000
  },
  "edges": [
    { "node": {...}, "cursor": "eyJpZCI6..." }
  ]
}
```

### FR-5: 기존 API 호환 레이어
- 기존 offset 방식 API 엔드포인트 유지 (deprecated 마킹)
- 마이그레이션 가이드 제공

## 3. 비기능 요구사항

### NFR-1: 성능
- 1,000만 건 테이블에서 어떤 페이지든 응답 시간 < 50ms
- 첫 페이지와 마지막 페이지의 응답 시간 차이 < 10%
- 메모리 사용량: 페이지네이션 처리당 < 5MB

### NFR-2: 보안
- 커서 위변조 방지 (HMAC 서명)
- SQL Injection 방지 (Prisma 파라미터 바인딩)
- limit 값 상한 제한으로 DoS 방지

### NFR-3: 안정성
- 커서가 가리키는 데이터가 삭제되어도 정상 동작
- 잘못된 커서 입력 시 명확한 에러 응답 (400 Bad Request)
- 만료된 커서 처리 정책

## 4. 사용자 시나리오

### 시나리오 1: 목록 첫 페이지 조회
**사용자**: API 클라이언트 개발자
**행위**: `GET /api/posts?limit=20` 호출
**결과**: 최신 20건의 게시물과 함께 `pageInfo`에 `endCursor`와 `hasNextPage: true` 반환. 클라이언트는 `endCursor`를 사용하여 다음 페이지 요청 가능.

### 시나리오 2: 다음 페이지 탐색
**사용자**: API 클라이언트 개발자
**행위**: `GET /api/posts?limit=20&cursor=eyJpZCI6MTAwfQ==` 호출
**결과**: 커서 이후 20건 반환. 데이터가 더 있으면 `hasNextPage: true`, 없으면 `false`. 중간에 새 데이터가 삽입되어도 누락/중복 없이 안정적으로 탐색.

### 시나리오 3: 잘못된 커서로 요청
**사용자**: API 클라이언트 개발자
**행위**: 위변조되거나 만료된 커서로 요청
**결과**: `400 Bad Request`와 함께 명확한 에러 메시지 반환. `{ "error": "INVALID_CURSOR", "message": "커서가 유효하지 않습니다." }`

### 시나리오 4: 대량 데이터 무한 스크롤
**사용자**: 모바일 앱 개발자
**행위**: 500만 건 데이터에서 연속적으로 커서 기반 페이지 탐색
**결과**: 모든 페이지에서 50ms 이내 응답. 메모리 사용량 안정적.

## 8. 제약사항 및 가정

### 제약사항
- 기존 Express 서버 구조를 크게 변경하지 않아야 함
- 기존 offset 방식 API는 deprecated 처리하되 즉시 제거하지 않음
- 커서는 클라이언트에게 불투명(opaque)해야 함

### 가정
- PostgreSQL을 사용하며 인덱스가 적절히 설정되어 있음
- Prisma ORM을 통해 DB에 접근
- 정렬 기준 필드(createdAt, id)에 복합 인덱스 존재
- Node.js 20+ / TypeScript 환경
- Jest를 테스트 프레임워크로 사용
